# AIShe v0.7.0 — product UX, routing, and reliability

AIShe v0.7.0 is the first full product-quality milestone after v0.6.5. It makes
the shell-versus-agent decision explainable, gives terminal output a consistent
semantic language, makes interactive selection and staged execution safer, and
turns compatibility and release claims into executable evidence.

This is an alpha, pre-1.0 release. It intentionally favors explicit authority,
inspectable behavior, conservative routing, and compatibility evidence over
silent convenience.

## Highlights

- Explain any routing decision with `aishe route -- <line>` or stable JSON with
  `aishe route --json -- <line>`.
- Force natural language with `?` and force one shell command with `!`. The
  legacy `#` natural-language prefix remains available during its documented
  migration window.
- Distinguish `AIShe · answer`, proposals, approvals, agent phases, warnings,
  failures, and final output with semantic color plus non-color textual cues.
- Choose dark, light, mono, or no-style output, with ANSI16, ANSI256, and
  truecolor degradation; static-motion and ASCII fallbacks are first-class.
- Filter long model and connection catalogs without losing the selected row.
  Printable keys filter; arrows, Ctrl-P/Ctrl-N, Home/End, and page keys navigate.
- Return suggested commands to the native zsh or Bash editing buffer before
  execution so history, completion, cursor movement, and highlighting remain
  available.
- Inspect all public automation paths through explicit, versioned JSON/JSONL
  contracts rather than undocumented root shapes.
- Run one qualification command for a recorded, identity-checked quick, local,
  Linux, release, or paid-live evidence profile.

## Routing and command interaction

The route decision is now a versioned contract with a route kind, reason,
source, and bounded diagnostics. Rust, generated zsh, Bash, the route CLI, and
the qualification corpora share the same policy and fixed points.

The declarative command registry now owns built-in slash commands and aliases,
surface availability, shell handoff, side-effect class, lifecycle state,
completion metadata, help metadata, and removed-command tombstones. Help,
completions, shell hooks, docs, and conformance tests derive from or verify that
registry, reducing drift between what AIShe says and what it accepts.

Routing remains deliberately local and deterministic. The classifier does not
call a model. A bounded one-time typo hint can explain a likely intended AIShe
command, but it does not execute or rewrite the input.

## Terminal UX and accessibility

The new terminal design system centralizes capability detection, semantic style
tokens, glyphs, layout, wrapping, truncation, theme selection, color depth,
motion, and machine-output policy. It provides:

- dark, light, mono, and no-style themes;
- automatic ANSI16, ANSI256, and truecolor selection;
- `NO_COLOR`, `TERM=dumb`, non-TTY, static-motion, and ASCII behavior;
- grapheme- and terminal-cell-aware layout for emoji, combining marks, and CJK;
- shared answer, proposal, approval, error, warning, and agent-state views;
- a visible `AIShe · answer` authorship boundary that remains meaningful after
  ANSI is stripped;
- bounded output and control-character sanitization for model-controlled text.

The connection/model picker now follows selection through a bounded viewport,
keeps focus visible in 1,000-row catalogs and narrow terminals, and separates
filtering from navigation. Promotion to a durable default remains an explicit
safe-negative confirmation.

Suggested commands are staged back into the native editor instead of being run
from a reduced prompt. zsh receives the command in `BUFFER`; supported Bash
versions use Readline staging or the documented recall path.

## Agent activity, authority, and safety

Agent output distinguishes connecting, planning, acting, waiting, recovering,
and finalizing phases. Focus mode remains concise; detail mode exposes bounded
attempt information. Changed-file summaries are bounded, and approvals state
the effective mode, scope, network policy, sandbox implementation, command,
effect, reason, and safe default without relying on color.

The `!` shell override prints a one-line, non-color warning that it bypasses the
AI safety gate. Destructive and host-scope approvals remain fail-closed.

Linux bubblewrap handling was corrected for the common case where a workspace
is nested under the user's home directory. AIShe masks home, creates the
namespace mount point, and directly rebinds the host workspace. Functional
Linux tests prove the workspace remains writable while sibling home credentials
remain hidden.

Managed provider capability detection now requests one coherent structured JSON
result and permits one bounded retry for malformed structured output. Paid-live
testing also aligned the YOLO acceptance harness with the managed
`aishe_run_command` proxy and the real workspace-authorization contract.

## Automation and persistent compatibility

All 23 public JSON or JSONL command paths now declare a schema version and have
an authoritative inventory covering framing, stdout/stderr, exit codes, bounds,
privacy, ownership, migration, and compatibility fixtures.

Some legacy inspection roots change shape in v0.7.0:

| Area | Previous shape | v0.7.0 shape |
| --- | --- | --- |
| Models | Bare array | Object with `schema_version` and `models` |
| Connections | Bare array | Object with `schema_version` and `connections` |
| Auth profiles | Bare array | Object with `schema_version` and `profiles` |
| Backend/runtime inspection | Raw object or array | Versioned object, using `runtime` where documented |
| Config/settings inspection | Raw config root | Versioned object with `config` |
| Audit replay | Historical raw records | Normalized versioned records; invalid or unsupported rows are skipped |

Automation should select the documented named field instead of depending on a
bare root. Prior v0.5 and v0.6 status/suggest fixtures remain tested alongside
the current v1 fixtures. Machine output remains ANSI-free.

Configuration schema 7 adds terminal theme, depth, Unicode, and motion
preferences. Migration is transactional and creates a timestamped backup.
Rollback must preserve config, task, session, audit, undo, history, OAuth, and
other user state; see the release-readiness rollback procedure before restoring
an older binary.

## Compatibility

The maintained compatibility claims for this release are deliberately scoped:

- macOS and Linux are exercised through native PTY qualification.
- zsh is the Tier A front end.
- Bash 5.x is Tier B; macOS Bash 3.2 is Tier B- with five documented
  alternatives and no claim of exact zsh parity.
- Linux tmux and screen transport paths passed the exact-candidate suite.
- One explicitly authorized SSH target passed staging, split escape input,
  resize propagation, terminal identity, and exact remote binary identity. This
  is evidence for that transport path, not a universal SSH-host claim.
- Fish receives generated completions but no native routing hook in this
  milestone.
- WSL2, native Windows, and named terminal-emulator matrices are not claimed as
  qualified by this release.

`NO_COLOR`, `TERM=dumb`, non-TTY, explicit no-style, static ASCII, and JSON
paths are regression-tested for zero ANSI or cursor-control bytes.

Native Bash provider calls now isolate child monitor-mode state and use private
files to return suggestions to the parent shell. This closes job-control and
EIO races observed under a real Bash 5.x PTY while retaining the documented
Bash 3.2 path.

## Architecture and maintainability

The 5,000-line binary entry point was split into focused CLI modules for args,
backend, connections, errors, hints, history, runtime, sessions, settings, and
status. Shell integration was split into reviewed source assets plus typed Rust
orchestration and registry fragments. Terminal views are pure renderers.

Every HTTPS client now uses `ureq` 3, and the terminal dependency graph has one
`crossterm` 0.29 line. Dependency-policy exceptions carry an owner, rationale,
review date, and intended removal condition.

The release also adds bounded local discovery hints, data-retention inspection
and deletion controls, threat-model evidence, lazy-loading checks, deterministic
boundary fuzzing, performance probes, compatibility decision records, and
document lifecycle enforcement.

## Qualification evidence

The functional paid-live candidate was tested from a clean Linux x86_64
checkout against `gpt-5.6-luna` with the credential supplied only through an
inherited environment variable:

- paid-live profile: **41 passed, 0 failed, 0 skipped** in 2,495.6 seconds;
- labelled natural-language behavior: **19/20**, then **20/20** on an
  independent repeat, with zero response-contract breaches;
- real-model fuzz: **84/84**, then **280/280** in the release repeat;
- a real managed YOLO tool call produced and verified a filesystem effect inside
  the Linux workspace sandbox;
- all-target tests, strict all-feature Clippy, Cargo deny, runtime install/live
  verify, provider contracts, soak, concurrency, resume, PTY, installer,
  credential-mode, Bash, and functional bubblewrap gates passed.

Local macOS changed-surface validation passed 572 all-feature library tests and
every integration target, 571 no-default-feature library tests and every
integration target, strict minimal-feature Clippy, formatting, 66 Python tests,
Ruff, and documentation/shell contracts. The release tag workflow independently
builds six target archives, four Linux packages, checksums, the pinned OpenCode
runtime assets, notices, an SPDX SBOM, and provenance, and publishes only after
every artifact job succeeds.

Qualification compares a validated 7–40-character binary commit prefix with the
full checkout commit, so a stale binary fails without assuming Git always emits
exactly seven abbreviated characters.

## Known alpha limitations and maintainer disposition

The maintainer directed publication of v0.7.0 on 2026-08-02 with the following
bounded risks accepted for this alpha release:

1. A failed managed tool followed only by a final model message can currently
   be summarized as a “recovered attempt,” even when no later effect succeeded.
   The paid harness correctly rejected the missing filesystem marker, so this
   does not convert a failed acceptance gate into a pass, but the interactive UI
   wording can overstate completion. Users must treat model completion prose as
   untrusted and verify requested effects. `AGENT-001` remains P0, owned by the
   AIShe maintainer, with a target disposition date of 2026-08-09.
2. A current-machine-state prompt produced a grounded command in 39 of 40
   labelled trials and a direct answer once. The declared 16/20 gate passed in
   both runs, but response-intent consistency remains `LLM-001` P1, targeted for
   2026-08-16.
3. The ONB-001 timed new-user observation was not completed. Existing setup,
   cancel/resume, first-answer, hints, and disclosure tests reduce but do not
   replace usability research. The research-only requirement is waived for this
   alpha release, owned by the AIShe maintainer, with follow-up targeted for
   2026-08-16.
4. Named emulator rows, WSL2, native Windows, and a native Fish hook remain
   unqualified and are excluded from v0.7.0 compatibility claims rather than
   represented as passes.

The implementation report and active plan retain the complete evidence,
negative findings, work breakdown, acceptance criteria, and post-qualification
queue.

## Install, verify, and roll back

Prebuilt archives cover Linux x86_64/aarch64 in GNU and static musl forms and
macOS arm64/x86_64. Debian and RPM packages cover amd64 and arm64. Each package
or archive has an attached SHA-256 checksum; runtime and supply-chain artifacts
are attached separately.

- Install guide: <https://github.com/billiondollarsolo/aishe/blob/main/docs/installation.md>
- Changelog: <https://github.com/billiondollarsolo/aishe/blob/main/CHANGELOG.md>
- Qualification and rollback policy: <https://github.com/billiondollarsolo/aishe/blob/main/docs/release-readiness.md>
- Full implementation evidence: <https://github.com/billiondollarsolo/aishe/blob/main/docs/design/NEXT_PRODUCT_UX_RELIABILITY_IMPLEMENTATION_REPORT.md>
- Active follow-up plan: <https://github.com/billiondollarsolo/aishe/blob/main/docs/design/NEXT_PRODUCT_UX_RELIABILITY_PLAN.md>

After installation, run `aishe doctor` and, for managed-agent use,
`aishe backend verify --live`. Rollback replaces binary/runtime artifacts only;
it must not delete or overwrite persistent user state.
